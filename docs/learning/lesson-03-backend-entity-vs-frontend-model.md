# Lesson 03：为什么后端实体类不能直接照着前端页面字段写

## 这节课学什么

这节课要解决一个非常关键的认知问题：

**为什么你前端页面里需要的字段，不能直接原样搬成后端数据库实体。**

你刚刚已经亲手做了一次非常真实的“踩坑前夜”：

- 你按前端页面感觉写了 `Order.java`
- 但数据库里的 `orders` 表结构不是那样

这不是你写错了，而是你现在碰到了前后端开发里最重要的一层边界：

**前端展示模型，不等于后端数据库实体模型。**

---

## 先看现在的冲突在哪里

你当前写的 `Order.java` 更像是“前端订单页想展示什么”。

比如你写了这些字段：

- `orderNo`
- `productName`
- `groupType`
- `amount`
- `pickupPoint`
- `receiverName`
- `mobile`

这套字段对前端来说很顺，因为页面就是这么展示的。

但是数据库里的 `orders` 表是另一种思路：

- `id`
- `user_id`
- `product_id`
- `total_price`
- `status`
- `pick_point_id`
- `group_buy_id`
- `create_time`
- `update_time`
- `deleted`

你会发现：

- 数据库里存的是 `product_id`，不是 `productName`
- 存的是 `pick_point_id`，不是 `pickupPoint`
- 存的是 `status` 数字码，不是中文文案
- 主键 `id` 直接就是订单号字符串，不是自增 Long

这不是谁对谁错，而是**站位不同**。

---

## 前端想要的是什么

前端页面的目标是：

**页面好展示，用户好理解。**

所以前端天然更喜欢这种字段：

- 商品名
- 自提点名称
- 状态中文
- 订单号
- 团类型文案

因为这些字段拿来就能渲染。

---

## 数据库想要的是什么

数据库的目标是：

**数据结构稳定、可关联、可查询、可扩展。**

所以数据库天然更喜欢这种字段：

- `product_id`
- `pick_point_id`
- `user_id`
- `status` 状态码

为什么？

因为数据库要考虑的是：

1. 商品名可能会变  
2. 自提点名称可能会变  
3. 状态文案可能会调整  
4. 关联查询和索引效率更重要  

所以数据库更倾向于存“稳定标识”，而不是直接存“展示文案”。

---

## 这时候后端该干什么

后端的职责不是只做数据库搬运工。

后端很重要的一件事就是：

**把数据库模型，转换成前端需要的展示模型。**

也就是说：

- 数据库里存的是 `product_id`
- 后端查出来后，再补成 `productName`

- 数据库里存的是 `pick_point_id`
- 后端查出来后，再补成 `pickupPointName`

- 数据库里存的是 `status = 1`
- 后端返回给前端时，可以变成：
  - `status = 1`
  - `statusText = "待成团"`

这就是为什么后端里常常会有：

- `Entity`
- `DTO`
- `VO`

它们不是多余，而是在做“不同层的模型转换”。

---

## 你现在要先记住一句话

**Entity 对数据库，DTO/VO 对前端。**

这句话现在先死死记住。

因为你接下来补订单、拼团、后台管理、AI 模块的时候，会反复碰到这个边界。

---

## 用你当前项目举个最贴切的例子

### 数据库里更适合怎么存

订单表里更适合存：

- `product_id`
- `pick_point_id`
- `status`
- `user_id`

### 前端页面更适合拿到什么

订单列表页更适合拿到：

- `productName`
- `pickupPointName`
- `statusText`
- `orderNo`

这两套字段，不应该强行做成完全一样。

---

## 所以当前阶段正确做法是什么

你现在应该先让 `Order.java` **向数据库现有表结构靠拢**。

而不是让数据库去迁就当前前端页面的字段命名。

原因很简单：

1. 数据库里 `orders` 表已经存在  
2. 现有表结构更像真实关系型设计  
3. 前端想要的展示字段，后面完全可以通过 DTO 再加工出来  

所以当前更合理的方向是：

**先保证 Entity 和表结构一致，再考虑返回给前端时怎么组装显示字段。**

---

## 下一步你会怎么改 `Order.java`

下一步我们会把 `Order.java` 改成更贴近当前 `orders` 表：

- `id` -> `String`
- 去掉 `orderNo`
- `productId` -> `Long`
- 去掉 `productName`
- `totalPrice` -> `BigDecimal`
- `status` -> `Integer`
- `pickPointId` -> `Long`
- `groupBuyId` -> `String`

也就是说：

这一步不是“删掉前端关心的字段”，而是把它们从 **Entity 层** 移出去。

以后这些展示字段会去 DTO/VO 层。

---

## 你现在这轮最重要的理解

你只要先把这句话讲顺就够了：

`数据库实体负责对表，前端展示字段以后通过 DTO/VO 组装，不一定直接存在 Entity 里。`
